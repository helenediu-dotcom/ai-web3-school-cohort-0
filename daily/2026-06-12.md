# 2026-06-12 学习笔记

## 今日主题：Day 26 — Agentic Commerce Track 入门

**目标**：理解 Agentic Commerce 的核心概念、协议栈和信任层，并关联现有实践。

---

## 一、什么是 Agentic Commerce

Agentic Commerce（智能体商业）不是"AI 帮你网购"，而是 **AI Agent 自主完成服务发现 → 信任判断 → 下单 → 支付 → 交付的全链路商业闭环**。

核心区别：

| 传统电商 | Agentic Commerce |
|---------|-----------------|
| 人浏览、比价、下单 | Agent 自主发现、评估、决策 |
| 信用卡/支付宝 → 平台担保 | 稳定币链上结算，无需账户 |
| 人对人/人对平台 | 机器对机器（M2M） |
| 支付和交付分离 | 支付即交付（x402：付款后直接返回资源） |

---

## 二、六层协议栈

Agentic Commerce 不是单一协议，而是一个六层技术栈：

```
┌──────────────────────────────┐
│  ⑥ 交付层 Fulfillment        │  ← 最大空白，尚无统一标准
├──────────────────────────────┤
│  ⑤ 支付层 Payment            │  ← x402 (Coinbase)、AP2 (Google)
├──────────────────────────────┤
│  ④ 授权层 Authorization      │  ← AP2、Session Key + Policy
├──────────────────────────────┤
│  ③ 下单层 Ordering           │  ← ACP (OpenAI × Stripe)
├──────────────────────────────┤
│  ② 信任层 Trust              │  ← ERC-8004 身份/声誉/验证
├──────────────────────────────┤
│  ① 发现层 Discovery          │  ← A2A、MCP、ERC-8004
└──────────────────────────────┘
```

**关键洞察**：下层（发现、信任）相对成熟，上层（交付）是当前最大空白。支付层正在快速标准化，x402 在 2025 年 Q4 实现了 10,780% 的月增长。

## 三、五大核心协议

### 1. A2A（Agent-to-Agent）— Google
- Agent 间互操作协议，基于 HTTP + JSON-RPC
- 让不同框架构建的 Agent 能互相通信、委派任务
- 定位：Agent 之间的互联网

### 2. MCP（Model Context Protocol）— Anthropic
- 统一工具与数据接入协议
- 连接 LLM/Agent 与外部系统（数据库、API、文件系统）
- 已是 agent-tool 交互的事实标准

### 3. ACP（Agentic Commerce Protocol）— OpenAI × Stripe
- 解决 Agent 如何帮用户完成购物结账
- 核心安全机制：**Shared Payment Token (SPT)**——Agent 和商家都看不到原始支付凭证
- 已落地：ChatGPT Instant Checkout（美国），即将接入 100 万+ Shopify 商家
- 开源（Apache 2.0），商户实现四个端点即可被任何 ACP 兼容 Agent 发现和购买

**ACP 交易流程**：
```
用户表达购买意图 → Agent 从商家 product_feed 发现商品
  → Agent 渲染 Stripe 结账 UI（聊天内嵌，不跳转）
  → Stripe 生成 SPT（限定商家、限定金额、有时效）
  → Agent 将 SPT 传给商家 → 商家调 Stripe 完成扣款
  → 商家负责履约（商家仍是 merchant of record）
```

### 4. AP2（Agent Payments Protocol）— Google
- 数字授权与支付指令协议
- 通过加密签名的授权凭证，绑定用户意图、授权范围和合规身份
- **Payment-Agnostic**：同时支持法币（信用卡/银行转账）和稳定币
- 定位比 ACP 更底层——回答"谁授权了这笔交易、责任归谁"

**ACP vs AP2**：
- ACP 回答："Agent 怎么在我的网站结账？"（ pragmatic commerce 集成层）
- AP2 回答："所有参与方如何信任 Agent 发起的支付？"（加密授权 + 责任归属）

### 5. x402 — Coinbase
- 复活 HTTP 402 "Payment Required" 状态码
- 稳定币原生支付，直接在 HTTP 层结算
- **无需账号、无需信用卡、无需 API Key**
- 支持低至 1 美分的链上微支付（Base L2，gas < $0.0001）

**x402 流程（7 步）**：
```
Client 请求付费资源
  → Server 返回 HTTP 402 + Payment-Required header（金额、地址、代币）
  → Client 签名支付授权（EIP-712 + EIP-3009 gasless USDC）
  → Client 重试请求，带上 Payment-Signature header
  → Facilitator 验证签名、提交链上交易、付 gas
  → 区块链结算（Base ~200ms）
  → Server 返回 HTTP 200 + 资源 + Payment-Response header（结算凭证）
```

**为什么重要**：这是第一个把支付嵌入 HTTP 协议层的标准。传统支付（信用卡、银行转账）慢、贵、需要账户/KYC——不是为机器间微支付设计的。x402 让支付像加载网页一样简单。

## 四、信任层：ERC-8004 Trustless Agents

### 核心命题

**Agent 之间如何互相信任？** 在没有中心化 gatekeeper 的情况下，一个 Agent 怎么判断另一个 Agent 是否可信？

ERC-8004（MetaMask + EF + Google + Coinbase 联合提出）用三个链上注册表解决：

### 1. Identity Registry（身份注册）
- 每个 Agent = 一个 ERC-721 NFT
- 全局唯一、可移植、抗审查的身份标识
- NFT 的 tokenURI 指向 Agent 的元数据（名称、能力、通信协议、端点）
- 所有权可转让、可委托

### 2. Reputation Registry（声誉记录）
- 任务完成后，客户提交结构化评价（0-100 分 + 标签 + 证据链接）
- 评价**不可篡改**（但可标记为 inactive）
- Agent **不能自评**
- 授权可设时效和频率限制（防刷分）
- 原始声誉信号存链上，复杂聚合/评分在链下

### 3. Validation Registry（验证记录）
- 高风险任务可请求独立第三方验证
- 支持三种信任模型：
  - **加密经济验证**：质押者重跑任务，错误则罚没
  - **zkML 证明**：零知识机器学习
  - **TEE 证明**：可信执行环境预言机
- 验证结果记录在链上，作为可验证证据

### 四级信任（T0-T3）

| 等级 | 场景 | 信任机制 |
|-----|------|---------|
| T0 | 低风险：只读查询、信息发现 | 仅身份 + 声明 |
| T1 | 中等风险：小额度可逆操作 | 签名意图 + 小额质押 + 最低声誉阈值 |
| T2 | 高风险：金融/医疗决策 | zk/TEE 证明 + 法定人数验证 + 质押/保险 + 持续监控 |
| T3 | 关键任务：生命攸关 | 多层监督 + 人机协同 + 监管级凭证 |

### 当前采用量
- ~21,500-30,000 Agent 已注册（2026 年初）
- Ethereum 主网 ~11,400，Base ~4,400，Gnosis ~2,700，BNB Chain ~2,300

## 五、关键洞察

### 1. 这不是"AI 购物"，这是机器经济的基础设施

Agentic Commerce 的本质不是让 ChatGPT 帮你买东西。它是为**机器与机器之间的自主商业**建立一套完整的协议栈——从身份、信任、定价、支付到交付。

### 2. 支付轨道分化：法币 vs 稳定币双引擎

- **法币轨道**（ACP + Stripe）：支撑主流人类消费场景
- **稳定币轨道**（x402 + USDC）：支撑 M2M 高频微支付

两者不是竞争关系。未来 Agent 可能同时走两条轨道——大额走法币（需要 chargeback 保护），微支付走稳定币（不需要）。

### 3. 信任不是二元的，是分级的

ERC-8004 的四级信任体系（T0-T3）是一个重要设计模式。不是"可信 vs 不可信"，而是"在什么风险等级下、用什么机制来建立信任"。

这和我们灰区引擎的五级风险分流是同一种思路——不是 approve/reject 二元决策，而是根据风险等级采取不同行动。

### 4. 交付层是最大空白

六层协议栈中，前五层都有标准/协议在推进，但交付层（Fulfillment）几乎是空白。问题：支付完成后，如何确保 Agent 收到正确的服务/内容？在无信任环境中，这比支付本身更难。

## 六、与现有实践的映射

| Agentic Commerce 概念 | 已有实践 | 状态 |
|----------------------|---------|------|
| 授权层 — Agent 权限约束 | 七维 Permission Policy + Session Key | ✅ 已有 |
| 授权层 — 签名前验证 | Pre-Tx Simulation + eth_call | ✅ 已有 |
| 授权层 — 风险分级 | 灰区引擎 5 级风险分流 | ✅ 已有 |
| 授权层 — 人机协同 | Confirmation 按风险等级交互 | ✅ 已有 |
| 信任层 — Agent 身份 | 无 | ❌ 缺失 |
| 信任层 — 声誉/验证 | 无 | ❌ 缺失 |
| 支付层 — 稳定币支付 | 仅 ERC-4337 UserOp（ETH 转账） | ⚠️ 部分 |
| 支付层 — x402 集成 | 无 | ❌ 缺失 |
| 下单层 — 结构化订单 | 无 | ❌ 缺失 |

**结论**：现有实践集中在**授权层**（安全侧）——这恰好是 Agentic Commerce 协议栈中我们做得最扎实的一层。缺失的是**信任层**（Agent 身份/声誉）、**支付层**（x402 标准支付）和**下单层**（结构化订单）。
