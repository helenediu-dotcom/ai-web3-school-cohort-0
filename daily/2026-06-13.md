## 二、核心架构

```
用户请求 → Agent 收到 HTTP 402 支付指令
  → ① 构造交易（to/ value/ data）
  → ② Safe Guard 前置校验（硬约束 + 软约束）
  → ③ Pre-transaction Simulation（eth_call + gas 预估）
  → ④ 风险分流：
       critical → 拒绝
       high → 人工确认
       medium → 灰区规则引擎自动决策
       low/trivial → 自动通过
  → ⑤ 链上支付（ERC-4337 UserOp → Smart Account）
  → ⑥ 等待区块确认
  → ⑦ 携带支付凭证重试 API → 获取付费数据
```

## 四、关键洞察

### 1. 安全基础设施的复用性超出预期

从"Agent 转账"切换到"Agent 支付 API"，**所有安全模块零改动直接复用**。Permission Policy 的七维约束、Safe Guard 的前置校验、Grey Zone 的规则引擎——这些设计当初针对的是通用 Agent 交易安全，但直接适用于商业支付场景。

这说明**安全层和业务层应该分离**。安全基础设施不应和具体场景耦合。

### 2. Agentic Commerce 六层协议栈的真实映射

经过实际编码，六层协议栈和现有实践的对应关系更清晰了：

| 层 | 标准协议 | 我们的实现 | 差距 |
|----|---------|-----------|------|
| ① 发现 | A2A, MCP | 硬编码支付指令 | 实际需要 Agent 自主发现付费 API |
| ② 信任 | ERC-8004 | Safe Guard + Grey Zone + Simulation | 缺少 Agent 身份注册/声誉系统 |
| ③ 下单 | ACP | 未覆盖 | 缺少结构化订单格式 |
| ④ 授权 | AP2 | Session Key + Permission Policy | 缺少加密授权凭证标准 |
| ⑤ 支付 | x402 | ERC-4337 UserOp | 非标准 x402，但流程等价 |
| ⑥ 交付 | 无标准 | 模拟 HTTP 200 | 行业最大空白 |

### 3. 本实践的核心贡献在授权层

我们的实践最强的是**授权层**——在 Agent 发起支付之前，用多层确定性规则（不是 LLM 判断）确保安全。这恰好是当前协议栈中最需要标准化、但最难标准化的一层。x402 和 ACP 解决了"怎么付"，但"该不该付"仍需要 Agent 自己判断。

## 五、代码要点

### `agentPayForApiData()` 核心函数

```typescript
// 输入：支付指令 + Agent Wallet + Session Key + Policy
// 输出：ApiData（成功）| PaymentFailed（失败阶段 + 原因）

async function agentPayForApiData(
  paymentInstr: PaymentInstruction,  // HTTP 402 响应
  wallet: AgentWalletInstance,       // Smart Account
  session: SessionKey,               // 临时授权
  policy: PermissionPolicy,          // 七维约束
  options?: CheckoutOptions           // autoConfirm / greyZonePolicy
): Promise<PaymentResult>
```

### 支付指令类型

```typescript
interface PaymentInstruction {
  amount: string;        // "0.001 ETH"
  amountWei: bigint;     // 1000000000000000n
  token: string;         // "ETH"
  recipient: Address;    // 收款方
  description: string;   // 服务描述
  apiUrl: string;        // 支付后重试的 API 端点
}
```
